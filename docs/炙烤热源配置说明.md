# 炙烤（GRILLED）热源配置说明

> 基于 `dev.celestiacraft.cmi.common.grill` 包。适用于 CMI 为 Create 工作盆（Basin）扩充的 `GRILLED` 加热条件。

## 一、判定顺序（务必先读）

工作盆读取热源方块时，`BasinBlockEntityMixin` 依以下顺序判定：

1. 方块自身带有 `create:blaze` 属性（即 `BlazeBurnerBlock.HEAT_LEVEL`）时，**直接交还原版逻辑**，按 `NONE / SMOULDERING / FADING / KINDLED / SEETHING` 取值；
2. 否则查询炙烤热源注册表，命中则返回 `GRILLED`；
3. 都不命中时，由原版 `#create:passive_boiler_heaters` 与 `BlockHelper.isNotUnheated` 兜底为 `SMOULDERING`，否则 `NONE`。

由此得到一条硬约束：**烈焰人燃烧室（`create:blaze_burner`）不能也不应被写入炙烤热源配置**。它自身参与原版 `HEATED` / `SUPERHEATED` 判定，一旦被当成 `GRILLED`，真实的 `KINDLED / FADING / SEETHING` 就再也读不到，原版加热配方会全部失效（1.3 版本的故障正是这样产生的，彼时 mixin 先判方块标签、后判属性）。

## 二、数据包写法

路径规则：`data/<命名空间>/cmi/grill_sources/<文件名>.json`，由 `GrillSourcesReloadListener`（`SimpleJsonResourceReloadListener`）扫描，支持 `/reload`，首尾均为服务端权威。

```json
{
	"priority": 0,
	"replace": false,
	"entries": [
		"minecraft:magma_block",
		"#cmi:grill_sources",
		{
			"block": "minecraft:campfire",
			"properties": {
				"lit": "true"
			}
		},
		{
			"block": "farmersdelight:stove",
			"properties": {
				"lit": "true"
			},
			"lenient": true
		}
	]
}
```

文件顶层字段：

- `priority`（整数，默认 `0`）：多文件合并时升序处理，数值小的先加入；同值按文件 id 字面序。
- `replace`（布尔，默认 `false`）：为 `true` 时先清空此前所有数据包条目（**不影响** Java / KubeJS 运行期注册）。
- `entries`（数组）：条目列表。文件顶层也可以直接是数组，此时等价于只给 `entries`。

条目三种形态：

1. `"ns:block"`——该方块的任意状态。
2. `"#ns:tag"`——该方块标签内任意方块的任意状态。
3. `{"block": "ns:block", "properties": {"lit": "true"}}`——仅在属性子集匹配时供热；用 `"tag"` 取代 `"block"` 即可对整条标签施加属性条件。

细节约定：

- `properties` 是**子集匹配**：未列出的属性不参与判断，只要求列出的属性值与方块当前状态一致。
- 属性值按字符串比较且忽略大小写，写成 `"true"`、`true`、`"TRUE"` 等价。
- `lenient`（布尔，默认 `true`）：方块本身不存在（未安装对应模组）时，无论 `lenient` 取何值都会告警并丢弃该条目。属性校验上，`true` 表示该属性在方块上不存在时去掉这条属性限制、降级为「任意状态」（仍会告警），以便同一份配置跨模组版本复用（部分灶台有 `lit`、部分没有）；`false` 表示属性不存在时整条声明作废，适合"配置写错就要立刻发现"的场合。

## 三、默认配置

内置 `data/cmi/cmi/grill_sources/default.json`，内容等价于：

- 引用 `#cmi:grill_sources` 标签：`minecraft:fire`、`minecraft:soul_fire`、`minecraft:magma_block`、`minecraft:lava`、`create:lit_blaze_burner`；
- `minecraft:campfire`、`minecraft:soul_campfire`、`farmersdelight:stove`、`mynethersdelight:nether_stove`、`kaleidoscope_cookery:stove`，均要求 `lit=true`。

若所有数据包文件都被 `replace` 清空，则退回 Java 内置的 `CmiGrillSources.BUILTIN_DEFAULT_JSON`（同内容），避免「空表即全部失效」。

## 四、KubeJS 写法

### 4.1 生成数据包文件（推荐，可落盘、可被 `/reload`）

```js
// kubejs/server_scripts/grill_sources.js
ServerEvents.highPriorityData((event) => {
	// 注意 id 里的双段 cmi：data/cmi/cmi/grill_sources/extra.json
	event.add(
		"cmi:cmi/grill_sources/extra",
		JSON.stringify({
			entries: [
				{
					block: "minecraft:furnace",
					properties: { lit: "true" },
				},
				{
					block: "minecraft:smoker",
					properties: { lit: "true" },
				},
			],
		}),
	)
})
```

`add` 的第二个参数是原始 JSON 文本；也可用 `event.addJson(id, JsonObject)` 传入已构造好的 `JsonObject`。

### 4.2 借用方块标签（最省事）

```js
ServerEvents.tags("block", (event) => {
	event.add("cmi:grill_sources", ["minecraft:furnace", "minecraft:smoker"])
})
```

标签内方块一律按「任意状态」供热；需要状态约束时请走 4.1 或 4.3。

### 4.3 运行期注册（不落盘，脚本重载即失效）

`CmiGrillSources` 已通过 `BindingsEvent` 绑定给 KubeJS：

```js
CmiGrillSources.register("minecraft:furnace")                          // 任意状态
CmiGrillSources.register("minecraft:furnace", { lit: "true" })         // 指定属性
CmiGrillSources.registerBlock(Blocks.FURNACE)                          // 直接给 Block
CmiGrillSources.registerBlock(Blocks.FURNACE, { lit: "true" })
CmiGrillSources.unregister("minecraft:furnace")                        // 按 describe() 前缀移除
CmiGrillSources.clearRuntime()                                        // 清空运行期注册（不动数据包）
CmiGrillSources.isGrillSource(blockState)                             // 单个状态查询
CmiGrillSources.all()                                                 // 当前生效条目快照
```

注意：

- 运行期注册只在**服务端**权威，请在 `server_scripts` 中调用；客户端由 `SyncGrillSourcesPacket` 在登录与 `/reload` 时自动同步。
- `unregister` 以字符串前缀匹配 `describe()`，`register("minecraft:furnace", {lit:"true"})` 之后 `unregister("minecraft:furnace")` 会连带移除所有以该方块开头的条目。

## 五、Java 写法

```java
CmiGrillSources.register("mymod:stove");
CmiGrillSources.register("mymod:stove", Map.of("lit", "true"));
CmiGrillSources.registerBlock(MyBlocks.STOVE.get());
CmiGrillSources.registerBlock(MyBlocks.STOVE.get(), Map.of("lit", "true"));
CmiGrillSources.unregister("mymod:stove");
CmiGrillSources.clearRuntime();
```

建议在 `FMLCommonSetupEvent` 或服务端 `ServerStartedEvent` 中调用；不要早于方块注册完成就访问 `all()` / `isGrillSource()`。

## 六、排错

- **原版加热配方突然失效**：检查是否有数据包把带 `create:blaze` 属性的方块（燃烧室）写进了炙烤热源；mixin 已改为属性优先，但仍不建议把原版热源放进炙烤表。
- **确认配置是否加载**：`/reload` 后看日志 `Loaded N grill source(s) from M file(s)`。
- **属性不生效**：确认属性名与方块状态定义一致（`state.getProperties()` 里的名字），值忽略大小写。默认 `lenient: true` 会把不存在的属性静默降级为「任意状态」，日志里有对应 warn；若希望拼写错误直接让整条声明作废，显式写 `"lenient": false`。
- **客户端表现不一致**：炙烤热源动画方块取自注册表首个可显示的条目的方块（`displayBlock()`，会跳过 `fire` / `soul_fire` / `lava`）；确认两端 CMI 版本与网络协议号一致。

## 七、实现要点与回归修复

本章记录代码里不再以注释形式保留的设计理由，改动代码前请先读这一章。

### 7.1 判定顺序为何改成「属性优先」

变更前 `BasinBlockEntityMixin` 的顺序是先判 `cmi:grill_sources` 标签、后判 `create:blaze` 属性，而标签里含 `create:blaze_burner`。燃烧室带属性，于是恒返回 `GRILLED`，`HeatCondition.testBlazeBurner` 里 `HEATED`（要求 `FADING|KINDLED|SEETHING`）与 `SUPERHEATED`（要求 `SEETHING`）都拿不到真实值，原版加热配方全部失效。

变更后：带 `create:blaze` 属性直接交回原版方法；否则查注册表；最后原版兜底。这条顺序是修复的实质，不能为了「让燃烧室也吃炙烤配方」而调换。

### 7.2 枚举追加常量的两个副作用

`HeatLevelMixin` 把 `GRILLED` 追加为第 6 个常量，`values().length` 由 5 变 6，带来两点影响：

- `nextActiveLevel()` 原实现是 `byIndex(ordinal % (values().length - 1) + 1)`，长度变化使 `SEETHING(4)` 算到 `byIndex(5) = GRILLED`（原版应循环回 `SMOULDERING`）。触发点是 `BlazeBurnerBlockEntity.applyCreativeFuel()`，创造模式喂烈焰蛋糕会出现热等级掉进 `GRILLED`。已在该方法注入固定 4 档循环修复：`GRILLED` 及以上不参与循环，直接回 `SMOULDERING`。
- `isAtLeast(HeatLevel)` 按 `ordinal()` 比较，`GRILLED(5) >= SEETHING(4)` 成立，因此炙烤热源在客户端会走最高一档的火焰渲染与粒子分支。这是有意保留的行为：炙烤被定位为高于 `SEETHING` 的档位，视觉上呈现最强火焰。

### 7.3 展示方块为何要跳过火焰与流体

`AnimatedBlazeBurnerMixin` 需要一个方块实例来渲染 JEI 动画。`fire`、`soul_fire`、`lava` 虽然可以做热源，但它们没有可用的方块模型，直接渲染会得到空模型或缺失纹理，因此 `CmiGrillSources.displayBlock()` 优先返回第一个非火焰/非流体的条目，只有全部条目都是这类方块时才退回第一个可用方块，最终兜底 `Blocks.FIRE`。

### 7.4 lenient 默认取 true 的取舍

默认宽容的理由是同一份配置要跨模组版本与不同整合包使用：`farmersdelight:stove` 与 `mynethersdelight:nether_stove` 在不同版本里是否有 `lit` 属性并不固定。代价是属性名拼写错误会被静默降级为「任意状态」，只在日志留一条 warn。需要严格校验的整合包应显式写 `"lenient": false`。

### 7.5 客户端同步的必要性与约束

服务端在 `AddReloadListenerEvent` 解析配置，客户端不参与数据包重载，但 JEI 动画与客户端侧调用都需要同一份表，因此由 `OnDatapackSyncEvent`（覆盖玩家登录与 `/reload`）下发 `SyncGrillSourcesPacket`。该包注册在 `CmiNetwork.register()` 末尾，既有包的 id 顺序不变，协议号仍为 `"2"`；两端必须使用同一版本的 CMI Core，混用旧版本 jar 会出现未知包 id。

### 7.6 为什么 `create:lit_blaze_burner` 可以留在炙烤表里

`LitBlazeBurnerBlock` 与 `BlazeBurnerBlock` 是两个不同的方块：前者只有 `FLAME_TYPE`（regular / soul）属性，没有 `create:blaze`，不参与原版 `HEATED` / `SUPERHEATED` 判定。把它列入炙烤热源不会截胡原版逻辑，因此 `#cmi:grill_sources` 标签里保留了它，而被移除的是带属性的 `create:blaze_burner`。
